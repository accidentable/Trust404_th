# 신분증 사본 없는 일당 지급

TRUST404 트랙 02 · DID/VC 기반 선택적 공개 + 봉인 전달

> 세금 한 푼 걷지 않는 하루짜리 알바에도 주민등록증 사본이 카톡으로 오간다.
> 사장님은 그 번호를 국세청에 넘겨야 할 뿐인데, 원본은 사장님 손에 남는다.

사장님에게는 **필요한 사실만**(성명, 만 18세 이상) 가고, 주민등록번호는 **국세청 공개키로 봉인**되어
사장님이 열지 못한 채 신고서에 첨부된다. 지급자를 보관자에서 **전달자**로 되돌린다.

---

## 1. 문제

학생이 교내 행사 스태프로 하루 일하고 일당 15만 원을 받는다. 지급자는 원천징수의무자라 신고 의무가
있고, 신분증 사본과 통장 사본을 카톡이나 구글폼으로 받는다.

| 목적 | 실제 필요한 것 | 누가 필요한가 |
|---|---|---|
| 지급명세서 제출 | 주민등록번호 13자리 | **국세청** |
| 계좌 명의 확인 | "예금주 = 지급 대상자" 참·거짓 | 사장님 |
| 연소자 확인 | "만 18세 이상" 참·거짓 | 사장님 |

**사장님 본인이 알아야 할 정보는 하나도 없다.** 그런데 실제로 넘어가는 건 주민번호 전체 + 주소 + 사진 +
발급일자가 박힌 이미지 한 장이다.

왜 문제인가:

1. **세금이 0원이어도 벌어진다.** 일당 18.7만 원 이하면 원천징수세액 없음. 그런데 지급명세서는 세금이
   0원이어도 제출 의무가 있고 미제출 시 가산세.
2. **사장님도 피해자다.** 주민번호는 법령 근거가 있어야 수집 가능하고, 개인정보위는 번호가 노출된 신분증
   사본 수집 자체를 피하라고 권고한다. 신고하려다 위법 소지와 보관 책임을 동시에 진다.
3. **사본은 실제로 악용된다.** KS한국고용정보 해킹(개인정보위 제재, 2026.04)으로 인사서류 약 5만 건 유출,
   그 서류가 주민등록등본·신분증 사본·통장 사본이었다. 경실련 피해자 고발대회(2022.07)에서는 촬영한
   운전면허증 사진만으로 본인 인증을 통과해 대출이 실행된 사례가 보고됐다.
4. **정상 요구와 사기 요구가 똑같이 생겼다.** 사기범도 "급여 지급에 필요하다"며 같은 걸 요구한다.

### 기존 시도와 한계

| 시도 | 한 것 | 한계 |
|---|---|---|
| 모바일 주민등록증 | 실물과 동일 효력, 제시형 인증 | 사본 보관이 필요한 업무엔 사용 불가. 제시가 보관 절차를 대체 못 함 |
| 휴대폰 본인확인 | 주민번호 없이 실명확인 | "본인 맞음"만 줌. 지급명세서용 13자리는 못 줌 |
| 캐치시큐 등 | 사본을 **안전하게 받는** 폼 | 원본은 여전히 존재. 위치만 카톡방 → 관리 서버로 이동 |
| 마스킹 권고 | 뒷자리 가리기 | 지급명세서엔 13자리 전부 필요 |
| EUDI Wallet / SD-JWT | 선택적 공개 (EU 표준) | 선택적 공개 자체는 이 프로젝트의 발명이 **아니다**. 국내 세무 절차의 "반드시 전달해야 하는 값" 문제는 다루지 않음 |

**공통 한계**: 주민번호가 지급자 손을 거쳐야 한다는 전제를 아무도 건드리지 않았다.

### 이 프로젝트의 기여 (딱 한 조각)

**국세청만 열 수 있는 봉인 필드.** 자격증명 안에 주민등록번호를 국세청 공개키로 암호화해 넣는다.
사장님은 그 값을 갖고 있지만 열 수 없고, 신고할 때 그대로 첨부하면 된다.

"안 보내기"와 "잠가서 보내기"는 다르다:

| | 주소 | 주민번호 |
|---|---|---|
| 방식 | 조각을 안 보냄 | 잠가서 보냄 |
| 사장님 | 존재도 모름 | 갖고 있지만 못 엶 |
| 국세청 | 안 감 | 열어서 봄 |

## 3. 무엇이 실제로 동작하고, 무엇이 목업인가

심사에서 가장 중요한 구분이라 먼저 밝힌다.

### 실제로 동작하는 것 (진짜 암호, 표준 포맷)

| 구현 | 표준 | 확인 방법 |
|---|---|---|
| 자격증명 발급 (Ed25519 서명, `did:key`) | IETF SD-JWT VC, W3C did:key | `npm run phase1` |
| 선택적 공개 (항목별 salt + SHA-256 다이제스트) | SD-JWT | `npm run phase2` |
| 재사용 방지 (nonce에 홀더 개인키 서명, `cnf`) | SD-JWT KB-JWT | `npm run phase3` |
| **봉인** (주민번호를 국세청 공개키로 암호화) | JWE `ECDH-ES+A256KW` / `A256GCM` | `npm run phase4` |
| 검증 11개 검사 + 레퍼런스 구현 교차 확인 | | `npm run verify:live` |
| 온체인 폐기 (`IssuerRegistry.sol`) | EVM | `cd contracts && forge test` |
| 기기 간 흐름 (폰 지갑 → QR → 사장님 화면) | | `/merchant` + `/wallet` |

### 목업인 것

암호는 진짜인데 **양 끝의 기관이 가짜**다.

- **주민센터**: 실제 주민등록 DB 가 없어 입력값 또는 더미로 발급한다. 서명은 진짜다.
- **국세청**: 서버가 복호화 키를 든 목업이다. 실제로는 홈택스가 이 봉인 포맷을 수용해야 한다.
- **세션 서버**: 시연 편의용 중계다. 실제로는 QR·딥링크(OpenID4VP)로 지갑과 검증자가 직접 통신한다.
- **홀더 키 보관**: 폰의 IndexedDB. 실제 지갑은 보안 하드웨어를 쓴다.

### 아직 안 한 것

- 계좌 VC (은행 발급 → "예금주 일치" 판정 → 통장 사본도 불필요)
- Sepolia 배포 (컨트랙트와 연동 코드는 완성. 자금 있는 키가 필요해 미배포. §7 참고)
- OpenID4VCI/OID4VP 프로토콜 구현 (포맷 호환만)

## 4. 빠르게 확인하기

```bash
npm install
npm run phase1   # 발급 → 검증 왕복. base58btc/did:key 자체 검사 포함
npm run phase2   # 선택적 공개. 조각 2/4만 보내도 검증 통과, 나머지는 해시만 남음
npm run phase3   # 재사용 방지. 남의 VP 재사용·다른 키 서명이 거부되는 것
npm run phase4   # 봉인. 사장님은 4경로 전부 실패, 국세청만 성공
```

각 스크립트는 통과/실패를 종료 코드로도 알려준다. 예를 들어 `phase4` 는 다음을 한 번에 검사한다.

```
경로                                        기대          결과
발급 시 평문 주민번호가 VC 에 남지 않음          없어야 함      ✓
사장님 자기 키로 열기                        실패해야 함    ✓
사장님이 국세청 공개키로 열기                  실패해야 함    ✓
봉인 탈취 후 공격자 키로 열기                 실패해야 함    ✓
봉인 변조 후 국세청이 열기                    실패해야 함    ✓
국세청 개인키로 열기                         성공해야 함    ✓
복호화 결과가 원문과 일치                     일치해야 함    ✓
```

서버를 띄우고 웹으로 보려면:

```bash
npm run dev     # http://localhost:3000
npm run demo:api   # 터미널에서 네 역할 API 를 1→4 순서로 실행
```

## 5. 화면

| 경로 | 누가 | 무엇 |
|---|---|---|
| `/` | 누구나 | 랜딩. 프로세스 여섯 단계, 역할 카드 |
| `/merchant` | 노트북 (사장님) | 사례 선택 → 요청 항목 조정 → **QR 띄우기** → 들어오는 제시가 목록으로 누적 |
| `/wallet?m=` | 알바생 폰 | QR 로 열림 → 키 생성 + 자동 발급 → 3칸 승인 → 제시 |
| `/issuer` | 발표자 | 1 주민센터: 번호를 찍어 발급, 분실 신고(폐기) |
| `/holder?h=` | 발표자 | 2 나: 지갑이 보관 중인 것 |
| `/verifier?h=&s=` | 발표자 | 3 사장님: 제시 받기 → 검증 → 봉인 열어 보기(실패) |
| `/tax?s=` | 발표자 | 4 국세청: 봉인 열기 → 지급명세서 |

역할 페이지 넷은 서로 다른 주체다. 단계 간 전달은 URL(`h`=holderId, `s`=sessionId)로만 하고,
각 페이지는 혼자서도 열린다. 응답은 요약으로 보이고 원본은 `JSON 보기` 아래에 접혀 있다.

### 지갑 승인 화면 (공개 범위 인터페이스)

사장님이 요청 항목을 바꾸면 이 화면이 그 자리에서 다시 그려진다. 하드코딩된 목록은 없다.

```
행사운영팀
일당 지급 및 원천징수 신고
─────────────────────────────
보여줄 정보
  ✓ 성명 · 홍길동
  ✓ 만 18세 이상 · 예
잠긴 채 전달 (상대는 열 수 없음)
  🔒 주민등록번호   국세청만 열 수 있음
보내지 않음
  ✗ 주소   ✗ 생년월일
─────────────────────────────
        [거부]    [제시하기]
```

용도별로 실제 필요한 항목을 상수로 두고, 그보다 더 요청하면 경고가 뜬다
(`⚠ 이 용도에는 주소가 필요하지 않습니다`). 사례 5개 중에는 주소나 생년월일이 **정당하게** 필요한 경우도
있다 — 예를 들어 주류 취급 알바는 청소년보호법상 만 19세 기준이라 "만 18세 이상"으로는 부족해 생년월일이
필요하다. "항상 최소만"이 아니라 "용도에 맞는 만큼만"이다.

## 6. 어떻게 동작하나

```
주민센터(Issuer) ──자격증명──▶ 지갑(Holder) ──제시──▶ 사장님(Verifier)
                                                          │
                                              봉인 전달 ───┴──▶ 국세청 (복호화)
                     폐기 레지스트리(온체인) ◀── 조회 ──┘
```

### 선택적 공개 (SD-JWT)

항목마다 `[salt, key, value]` 조각을 만들고 **그 해시만** 본체에 넣어 서명한다. 제시할 때 조각 원본을 같이
주면 검증자가 해시를 재계산해 대조한다. 안 준 항목은 다이제스트만 남아 **이름도 값도 알 수 없다**.

salt 가 필수인 이유: `isOver18` 처럼 값의 경우의 수가 적으면 salt 없이는 대입으로 맞힐 수 있다.

검증자 쪽에서 실제로 확인할 수 있다 (`npm run phase2` 출력):

```
_sd 배열에는 다이제스트 4개가 있는데 조각은 2개만 왔다.
사장님이 아는 것: 그런 항목이 2개 있다는 사실, 각각의 SHA-256 다이제스트
모르는 것: 항목의 이름, 항목의 값
```

### 봉인 (JWE)

```
alg  ECDH-ES+A256KW
enc  A256GCM
aud  국세청
epk  (매 봉인마다 새로 만드는 임시 공개키)
```

발급 시점에 주민등록번호를 국세청 X25519 공개키로 암호화한다. 발급 이후 평문 번호는 어디에도 없다
(`phase4` 가 자격증명 전체를 문자열 검색해 확인한다). ECDH-ES 는 발신자가 매번 임시 키쌍을 만들어 쓰고
버리므로, 주민센터조차 봉인 후에는 같은 값을 다시 열 수 없다.

> 국세청 키만 X25519 인 이유: Ed25519 는 서명 전용이라 ECDH 키 합의를 할 수 없다. 같은 Curve25519
> 계열의 X25519 를 쓰고, did:key multicodec 만 `0xec01` 로 다르다.

### 재사용 방지 (Holder Binding)

자격증명의 `cnf` 에 홀더 공개키가 박혀 있다. 제시할 때 검증자가 준 nonce 에 홀더 개인키로 서명한다(KB-JWT).
검증자마다 다른 nonce 를 주므로 사장님이 받은 제시를 다른 곳에 복사해도 통과하지 못한다.

`sd_hash` 는 그 제시의 조각 구성 전체를 묶는다. 유효한 KB-JWT 를 떼어 다른 조각 묶음에 붙이는 것도 막힌다.

### 폐기 (온체인)

체인에 올라가는 것은 **폐기 인덱스와 여부뿐이다. 개인정보는 한 글자도 없다.** 인덱스는 난수로 배정한다
(순차면 발급 순서와 시점이 드러난다). 인덱스↔사람 매핑은 발급기관만 안다.

**왜 체인인가**: 폐기 확인을 발급기관에 물어보면 발급기관이 "이 사람이 지금 어디서 신분증을 쓰는지" 알게
된다. 그걸 막으려고 쓴다. 그래서 사장님 브라우저가 우리 서버가 아니라 **RPC 를 직접 읽는다** — 서버는
발급기관 키를 들고 있으므로 서버에 물으면 같은 문제가 생긴다.

### 검증 (사장님 브라우저에서)

내부 검사 11개를 화면에서는 4줄로 묶는다.

```
✓ 주민센터 서명 확인   (발급기관 신뢰, EdDSA 서명, vct, 조각 해시 대조, 레퍼런스 교차 확인)
✓ 유효기간 정상
✓ 본인 제시 확인      (cnf 서명, nonce, aud, sd_hash)
✓ 폐기 여부 확인      (레지스트리 조회)
```

**검증은 아무에게도 묻지 않는다.** 필요한 것이 전부 제시 안에 있기 때문이다 — 발급기관 공개키는 `did:key`
식별자 자체에서 나오고, 홀더 공개키는 `cnf` 에 있고, 다이제스트는 본체에 있다. 밖에 묻는 것은 폐기 확인
하나뿐이고, 그것도 발급기관이 아니라 체인에 묻는다.

순수 계산 시간 (네트워크 제외, 참고용):

```
발급 (서명 + 봉인)     9.9 ms
제시 (조각 선택 + KB)  3.5 ms
검증 (11개 검사)      15.1 ms
봉인 해제              0.4 ms
```

## 8. 공격 시연

| 공격 | 방법 | 결과 | 확인 |
|---|---|---|---|
| 서명 위조 | 본체 JWT 한 글자 변조 | ❌ 서명 불일치 | `phase1` |
| 값 변조 | 조각의 value 변경 | ❌ 해시 불일치 | `phase1` |
| 만료 | exp 지난 자격증명 | ❌ 만료 | `phase1` |
| 가짜 발급기관 | 다른 키로 서명한 자격증명 | ❌ 신뢰 목록에 없음 | `phase1` |
| 재사용 | 받은 제시를 다른 검증자에게 제출 | ❌ nonce·aud 불일치 | `phase3` |
| 키 위조 | 훔친 자격증명에 자기 키로 KB-JWT 서명 | ❌ cnf 불일치 (nonce·aud 는 통과) | `phase3` |
| 봉인 탈취 | 봉인만 빼내 다른 키로 열기 | ❌ 복호화 실패 | `phase4` |
| 봉인 변조 | ciphertext 한 글자 변경 | ❌ AEAD 태그 검증 실패 | `phase4` |

### 막지 못하는 것 (정직하게)

- **사장님이 알게 된 "이름"을 메모하는 것.** 기술로 막을 수 없다. 대신 넘어가는 양이 이름 하나뿐이다.
- **검증자와 제3자의 실시간 중계 공격.** `aud`(검증자 신원) 서명으로 완화만 된다. 현재 `aud` 는 요청의
  `verifier` 문자열이라 암호학적 신원이 아니다. 완전히 막으려면 `aud` 를 검증자 DID 로 바꾸고 요청 자체에
  서명해야 한다.
- **컨트랙트 소유자 키 탈취.** 폐기가 조작될 수 있다. 체인이 주는 보호의 정체는 "차단"이 아니라
  **"몰래 못 함"** 이다.

## 9. 한계

1. 현행 소득세법상 지급명세서에 주민번호 기재가 필요하므로, **번호를 없애는 게 아니라 사업주를 거치지
   않게 하는 것**이다.
2. 실제로 동작하려면 홈택스가 이 봉인 포맷을 수용해야 한다. 여기 국세청은 목업이다.
3. 세무조사 증빙으로서의 법적 인정은 별도 문제다. 실무자는 사본을 증빙으로 원하고, 서명된 자격증명이 그
   역할을 하려면 세무 당국의 인정이 필요하다. 지금은 근거가 없다.
4. 도입 주체가 소상공인이라 확산 부담이 크다.
5. **선택적 공개는 EU 표준(EUDI/SD-JWT)의 기본 기능이며 이 프로젝트의 발명이 아니다.** 기여는 봉인 필드
   하나다.
6. 세션 서버는 시연 편의용이다. 서버가 nonce 를 대신 발급하고 제시를 중계하므로, 서버를 믿지 못하면 이
   경로의 재사용 방지도 믿을 수 없다. 서버는 제시를 열어 보지 않고 검증은 사장님 브라우저가 하지만,
   중계자라는 사실 자체는 남는다.
7. RPC 제공자는 어느 인덱스를 조회했는지 볼 수 있다. 완전한 조회 프라이버시는 아니다.
8. 폰 경로는 HTTPS 에서만 동작한다. `crypto.subtle` 이 보안 컨텍스트에서만 존재하기 때문이다.

| QR | `qrcode` |
| 세션 서버 | Express (단일 인스턴스, 메모리) |

`base58btc` 는 의존성을 늘리지 않으려고 직접 구현했고, W3C did:key 문서의 예시 벡터로 자체 검사한다
(`phase1` 0단계).

### 레포 구조

역할 구분이 코드에서 드러난다.

```
src/
  issuer/      주민센터 — 발급 키, 발급 로직, 폐기 인덱스 배정
  holder/      지갑 — 홀더 키, IndexedDB, 승인 계획, 제시
  verifier/    사장님 — 검증 11개, 공개 범위 감사, KB-JWT 검증
  tax/         국세청 — 복호화 키
  shared/      타입, crypto, did:key, SD-JWT, 봉인, 폐기 레지스트리
  ui/          랜딩, 사장님 화면, 폰 지갑, 역할 페이지 4개
server/        세션 서버, 기관 키, 역할 API
contracts/     IssuerRegistry.sol + Foundry 테스트
scripts/       phase1~4, demo:api, verify:live
```

한 저장소지만 각 역할은 자기 키만 갖고 서로의 비밀에 접근하지 않는다.

## 11. AI 사용 내역

이 프로젝트는 **Anthropic Claude (Claude Code)** 를 사용해 개발했다. 구체적으로:

- **설계 결정**: 사람이 `CLAUDE.md` 에 문제 정의, 데이터 모델, 암호 설계, UI 명세를 먼저 작성했다.
  봉인 필드라는 핵심 아이디어, 트랙 선택, 시연 시나리오는 사람이 정했다.
- **코드 작성**: 대부분의 구현 코드를 Claude Code 가 작성했다. 사람이 단계별로 요구사항을 주고
  (Phase 1~6), 결과를 검토하고, 방향을 수정했다. UI 는 여러 차례 전면 재작성을 지시했다.
- **검증**: 각 단계의 동작 확인(`phase1~4`, 브라우저 테스트, anvil 연동 테스트)은 Claude Code 가
  실행하고 결과를 보고했다. 테스트가 잡아낸 버그(요청 충족 판정에서 봉인 필드 누락, 서버 재시작 후
  QR 무효화 등)도 그 과정에서 수정했다.
- **문서**: 이 README 를 포함한 문서 초안을 Claude Code 가 작성하고 사람이 검토했다.

세무 관련 사실관계(원천징수 세율, 지급명세서 제출 기한, 개인정보위 제재 사례)는 사람이 조사해
`CLAUDE.md` 에 정리한 것을 근거로 썼다.
