# SabonX 앱 구현

## 경로

- `/`: 기존 랜딩 구조와 대화 연출을 유지. 주요 CTA와 설명을 월 급여 흐름에 연결.
- `/app`, `/wallet`, `/merchant`: 새 앱. `/app?role=merchant`로 사업주부터 시작 가능.
- `/legacy/merchant`, `/legacy/wallet`: 이전 QR 흐름의 화면.
- `/issuer`, `/holder`, `/verifier`, `/tax`: 이전 실험 페이지. 새 업무 흐름의 주 경로가 아님.

## 데이터와 권한

새 데모 생성 시 worker/merchant/admin capability를 발급합니다. 근로자용 공유 링크에는 worker capability만 포함됩니다. 사업주 요청은 고정된 가상 사업체와 해당 데모에 등록한 근로자 공개키에 연결됩니다. 전화번호는 고정된 테스트 라우팅 값이며 실제 소유 인증이 아닙니다.

근로자 기기는 room별 Ed25519 키를 생성하고 IndexedDB에 보관합니다. 발급 요청에는 공개키와 그 키로 서명한 발급 proof가 필요합니다. 기관은 가상 신원정보를 `cnf.jwk`와 함께 실제로 서명합니다. 이미 연결된 키를 다른 키로 바꿀 수 없습니다.

신고 요청 JWS에 금액·대상월·사업체·대상 공개키·nonce를 포함합니다. 지갑은 요청 서명을 검증하고 화면의 내역과 대조합니다. SD-JWT 제시는 이름만 공개합니다. 주소·생년월일·가상 사진·문서 발급일·발급기관은 공개 조각을 보내지 않습니다. 주민번호 JWE는 발급기관 서명에 포함됩니다.

승인 JWS는 요청 토큰의 SHA-256 해시와 SD-JWT+KB-JWT 전체의 해시를 묶습니다. 세무 검증기는 신뢰 발급자, VC 유효기간, 소유 키, nonce/audience, 선택 공개 무결성, 폐기 상태, 대상 근로자 키, 승인 서명을 확인합니다. 접수 때 요청을 일회성으로 소비하며 동시 중복 제출을 방지합니다. 영속 DB로 확장할 때는 해당 상태 변경을 트랜잭션으로 구현해야 합니다.

사업주 응답은 요청 내역, 최소 검증 결과, 이름과 서명된 접수증만 포함합니다. VP·승인 토큰·복호화한 주민번호를 요청 레코드에 저장하지 않습니다. 접수증은 모의 세무 서명키로 서명됩니다.

## 폐기와 재발급

근로자 변경 요청을 모의 기관이 자동 승인하거나 기관 시뮬레이션 capability로 주소 또는 이름 변경을 확인합니다. 기존 VC의 폐기 트랜잭션 성공을 기다린 뒤 변경된 신원정보와 업데이트 필요 상태를 기록합니다. 근로자는 기존 키로 새 VC를 발급받습니다. 기존 VC는 비교 시연을 위해 지갑에 보관하지만 정상 제출은 최신 VC를 사용합니다. 재발급 실패 시 기존 증명은 계속 폐기 상태이며 재시도할 수 있습니다. 과거 접수증은 취소하지 않습니다.

`statusIndex`는 48비트 난수이며 프로세스 내 중복을 방지합니다. 운영에는 영속 저장소의 uniqueness 제약이 필요합니다. 체인 미설정 시 명시된 로컬 스텁으로 동작합니다. 체인 조회 실패는 유효로 간주하지 않습니다.

## 검증


pm run test:payroll` (서버 실행 필요): 실제 발급, 선택 공개, 접수증 서명 검증, 역할 권한, 승인 내용 변조, 다른 키, 동시 중복·재사용, 정보 변경 폐기, 재발급, 사업주 응답의 정보 최소화를 확인합니다.

더보기에서 승인 바꿔치기 검사는 요청 해시가 다른 승인 서명을 만들어 서버의 결합 검증을 실행합니다. 이전 VC 검사는 새로운 pending 요청의 nonce로 정상 서명하여 폐기 검증에서 거절되는지 확인합니다. 같은 요청 재사용 검사와 구분합니다.

## 운영과의 차이

데모는 24시간 메모리 세션, 세션당 50개 요청, 서버당 최대 200개 세션입니다. 기관 및 복호화 키는 동일 서버 프로세스이며 별도 기관 서버/KMS 격리 전입니다. HTTPS 배포, 앱 코드 신뢰, 지갑 복구, 실명·번호 소유 확인, 만료 자격증명 갱신 정책, 실서비스 인가 및 실제 세무 규칙은 운영 설계 대상입니다. 앱에서 명시하는 서명과 암호 검증은 실제이며 법적 신고 효력은 없습니다.

## VC 보관 (2026-09-20 변경)

`/app` 발급 API는 VC를 발급 응답으로 한 번 전달하고 서버 세션에는 폐기 식별자와 만료시각만 남깁니다. VC 원문·공개 조각·JWE 복사본은 저장하지 않습니다. 브라우저 IndexedDB가 VC를 보관합니다. 발급 응답은 no-store입니다. 다시 발급하면 이전 식별자를 폐기한 뒤 새 VC를 생성하며, 실패 후 재시도에도 폐기 상태가 유지됩니다. 이는 서버 복사본 복구/동기화가 아닙니다. 개인키까지 잃으면 현재 데모에서는 새 세션이 필요합니다. 모의 기관의 가상 원천 신원정보는 그대로 유지합니다. 이전 실험용 역할 API의 서버 지갑은 별도 레거시 기능이며 기본 비활성화합니다.

## 근로자 변경 요청
근로자 공유 링크에서도 /change-request로 이름·주소 변경을 요청합니다. 모의 기관 자동 승인은 데모 처리이며 실명정보 검증을 의미하지 않습니다. 폐기 성공 후 정보가 변경되며 재발급은 지갑에서 실행합니다. 사업주 권한 요청은 거절합니다. 9월 접수 → 10월 인상 급여 요청 → 주소 변경 요청 → 이전 VC 제출 거절 → 재발급 → 같은 10월 요청 접수 순으로 시연할 수 있습니다.
